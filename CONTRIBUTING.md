# Contributing

Thanks for looking. This is a security component, so the bar is "can a reviewer see why this is
safe", not "does it work on my machine".

## Setup

```bash
brew install uv
make setup
make up
make test
```

## The rules that keep it honest

These are enforced by review and, where possible, by tests. The full list is in
[CLAUDE.md](CLAUDE.md).

1. **Deny by default and fail closed.** A new dependency or stage needs a test proving that
   its failure denies the call.
2. **Every behaviour change comes with tests in the same change**, including one showing the
   attack is blocked and one showing the normal case still works. Never skip, delete or loosen
   a test to make it pass, and never mock the component under test.
3. **No secrets in code, logs, spans, metrics or audit rows.** There are canary tests; add your
   new sink to them.
4. **No typed numbers.** Benchmarks and scores come from scripts that write to `results/`; the
   README's table is generated by `make readme-results`.
5. **Upstream text is data.** Never execute, eval or follow a tool description or result.
6. **Keep the pipeline order.** Each stage is a small class with one async method.
7. **If you cite a test in the threat model, it must exist** -
   `tests/unit/test_threat_model_links.py` checks.

## Before you open a pull request

```bash
make lint
make test
make security
```

If you changed scanning or policy, also run `make redteam` and commit the new `results/` files.
Write the reasoning for anything non-obvious in `docs/decisions.md`.

## Reporting a vulnerability

Please do not open a public issue. Contact the maintainer privately with a description and, if
you can, a failing test.
